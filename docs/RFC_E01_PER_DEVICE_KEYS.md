# RFC E-01 — per-device ключи вместо host jwt_secret

> Статус: **draft** · Автор: Sisyphus (2026-08-25) · Обсуждение: vynkor (host) + wire
> Источник: AUDIT.md №6 / ROADMAP.md E-01. R-03 уже закрыл хранение секрета на
> устройстве (Keystore AES-GCM, без бэкапов); этот RFC устраняет саму
> избыточность доверия.

## Проблема

Сегодня при паринге устройство получает **общий секрет всего хоста**
(`jwt_secret`), из которого:

1. выводится per-session frame-MAC ключ (`derive_session_key(secret, nonce,
   plugin_id)`), и
2. **можно минтить JWT любого устройства** (секрет хоста = секрет подписи
   dev-токенов).

Компрометация телефона = компрометация всех устройств и способности хоста
выдавать доверие. Устройству не нужно право минтить токены — ему нужен только
собственный идентитет.

## Требования к решению

- T1. Устройство после паринга не знает материала, пригодного для минта чужих токенов.
- T2. Frame-MAC остаётся симметричным и дешёвым (протокольное ограничение v1).
- T3. Отзыв устройства на стороне хоста без ротации секрета «всего мира».
- T4. Совместимость с proto v1.6 там, где это возможно; версия протокола паринга повышается точечно.
- T5. Миграция существующих спаренных устройств без ручного перепаринга, где достижимо.

## Предлагаемая схема (v2 паринга)

**Per-device secret, выданный хостом.** Хост генерирует случайный 32-байтный
`device_secret` для каждой пары `(device_id, cap-set)`, сохраняет у себя
(таблица devices: id ↔ secret ↔ status) и отдаёт устройству через QR.

```
host $ vyn device connect            # как сейчас
  └─ mint device JWT (sub=device_id, ограниченные claims)   ← уже так
  └─ generate device_secret (CSPRNG)                        ← НОВОЕ
  └─ store: devices[device_id] = { device_secret_hash?, status }  ← НОВОЕ
QR payload v2: { v:2, host_url, jwt_token, device_secret, cert_pem }
```

- **Frame-MAC**: `derive_session_key(device_secret, nonce, plugin_id)` — та же
  функция, другой входной секрет (T2 соблюдён, изменения только в том, *что*
  хост кладёт в nonce-ответ и что считает общим секретом).
- **Минт токенов**: `jwt_secret` остаётся только на хосте и больше не покидает
  его (T1).
- **Отзыв**: хост помечает запись `revoked`; register с таким device_id
  отклоняется (T3). Ротация скомпрометированного `device_secret` =
  новый QR-паринг этого одного устройства.

### Почему не асимметрика (Ed25519-подпись кадров)

Рассматривалась: устройство держит приватник, хост — публичный ключ.
Отклонено для v1 схемы: подпись/верификация каждого кадра дороже HMAC на
мобильном CPU при стриминге PCM 50 fps, а главный выигрыш T1 достигается и
симметричным per-device секретом. Асимметрию оставить как v3-опцию для
устройств, которым нужен zero-knowledge паринг (секрет вообще не передаётся).

## Изменения по репозиториям

| Репозиторий | Изменение |
|---|---|
| **vynkor-wire** | `PairPayload`-схема вне proto (это QR JSON) — изменений framing/proto НЕ требуется; `PROTOCOL_VERSION` остаётся 1.6, т.к. кадры совместимы |
| **vynkor** (хост) | таблица devices (+CRUD в CLI `vyn device connect/list/revoke`); при register-ack использовать `device_secret` вместо глобального `jwt_secret` в derive_session_key; reject по статусу revoked |
| **vynkor-client-android** | ничего структурно: поле `jwtSecret` профиля становится «per-device secret»; переименовать в UI (`HostProfile.jwtSecret` → `deviceSecret`) + миграция данных |
| **SDKs** (rust/cpp/python) | синхронно переименовать параметр конфигурации, поведение то же |

## Миграция

1. Хост обновляется первым: продолжает принимать старые подключения по
   глобальному секрету (флаг `legacy_pairing: true`, default on).
2. Клиент vNext при register добавляет claim `pairing_v2: true`; хост отвечает
   ack-расширением `{ device_secret_issued }` — устройство прозрачно
   перепаривается при следующем QR-скане.
3. Принудительный обгон: `vyn device revoke --legacy-all`.

## Open questions

- Q1: хранить ли на хосте `device_secret` открыто (нужен для derive_session_key)
  или только hash + KDF-вывод MAC-ключа на лету? Открытое хранение эквивалентно
  сегодняшнему риску БД хоста; hash-only требует, чтобы KDF делало обе стороны
  от одного материала — предложить HKDF(device_secret, "frame-mac" || plugin_id).
- Q2: один секрет на устройство или на пару (device, capability)? На устройство
  проще; per-cap даёт гранулярный отзыв — решить до имплементации.
- Q3: ротация `jwt_secret` хоста перестанет разрывать все устройства — проверить,
  что это желаемое следствие.
