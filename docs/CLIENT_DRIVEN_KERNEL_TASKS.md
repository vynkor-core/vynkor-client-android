# Что нужно ядру, чтобы клиент стал продуктом

*2026-08-26 · точка зрения Android-клиента (D-14) · ядро пока НЕ трогаем — это план*

Клиентская волна F закрыта (виджеты, темы, ru/en, настройки чата, быстрый свитч
хостов). Всё, что дальше делает приложение «удобным для чужого человека», упирается
в хостовую сторону. Этот документ фиксирует чего именно и в каком порядке.
Родственный документ: [RFC E-01](RFC_E01_PER_DEVICE_KEYS.md) (per-device ключи).

## Почему сегодня приложение всё ещё «для своих»

| Барьер | Следствие |
|---|---|
| Паринг требует `vyn token mint …` из CLI и ручного заполнения 4 полей | человек без терминала не подключится никогда |
| На телефоне лежит мастер-ключ хоста (`jwt_secret`) | нельзя давать приложение никому, кому не доверяешь весь хост |
| Ответы AI приходят целиком | локальный typewriter маскирует задержку; ощущение «медленно» |
| Голос работает только внутри открытого чата | нет сценария «команда без экрана» — ради него и существует агент |

## P0 — блокеры для «просто дать другу APK»

### 1. Паринг без CLI (pairing ticket)
- Ядро: команда `vyn device pair [--ttl 5m]` и/или `POST /devices/pair` →
  **одноразовый ticket** (single-use, TTL ~5 минут). Payload QR v2 =
  `{v:2, ws, ticket}` вместо полного набора секретов.
- При первом подключении с ticket ядро само выпускает device JWT и регистрирует
  устройство; в вебе/CLI — список устройств с отзывом.
- Затронуто: `vynkor` (REST+CLI), `vynkor-wire` (поле версии payload),
  клиент **уже готов** (`PairingPayload.parseWithReason`, R-02 подтверждение).
- Оценка: 6–10 ч.

### 2. E-01: per-device ключи вместо host jwt_secret
- Полностью описано в [RFC E-01](RFC_E01_PER_DEVICE_KEYS.md): Ed25519-пара на
  телефоне, публичный ключ уезжает в ticket'е, ядро проверяет подпись challenge.
- Это **главный** security-стоппер для распространения: после E-01 компрометация
  телефона ≠ компрометация хоста.
- Оценка: кросс-репо, XL (см. RFC).

### 3. Стриминг ответов AI (`{id}.chat`)
- Сегодня: request/response, ответ приходит одним куском. Нужно: поток токенов
  (новые типы фреймов в wire, например `CHAT_DELTA`) + отмена запроса
  (`chat.cancel`) — пользователь тапнул «стоп», а запрос уже не должен жечь токены.
- Клиент адаптируется за час: typewriter станет реальным стримом.
- Затронуто: `vynkor-wire` (фреймы), `vynkor` (ai-plugin прокси), ai-плагин.
- Оценка: 8–12 ч.

## P1 — сценарий «без рук»: wake word и голосовые команды

Wake word детекция останется на телефоне (локальная KWS, микрофон в режиме
low-power) — ядру тут ничего. Но вокруг неё ядру нужны:

### 4. Assistant-session контракт
- Быстрое переоткрытие mic-сессии после триггера (бюджет < 300 мс от wake до
  стрима); сегодня старт сессии проходит полный handshake пермишенов.
- События к телефону: `partial_transcript` (промежуточное распознавание),
  `turn_end` (сервер решил, что фраза закончилась), `tts_interrupt` (barge-in:
  новая реплика глушит текущий TTS на телефоне).
- Единый пайплайн на хосте: STT → agent/router → TTS без обязательного чата,
  чтобы «выключи свет» исполнялась как capability-call, а не как болтовня.
- Оценка: 12–20 ч (ядро + плагины).

### 5. Аудит capability-вызовов на устройстве
- Событие `capability_used {cap, ts, origin}` обратно на телефон → экран
  «кто и когда спрашивал мою геолокацию». Без этого чувствительные пермиссии —
  черный ящик, и их страшно выдавать.
- Затронуто: `vynkor` (event bus → device route). Клиент уже имеет канал событий.
- Оценка: 4–6 ч.

## P2 — гигиена протокола

| # | Задача | Суть |
|---|---|---|
| 6 | Version negotiation в handshake | клиент шлёт `protocol_version=1.6`; поведение при расхождении сейчас не определено — договориться min/max |
| 7 | Судьба команд офлайн-устройству | host→device request при отвале: честная ошибка сразу или очередь с TTL — сейчас похоже на таймаут-тишину |
| 8 | TLS-онбординг | self-signed CA + отпечаток сертификата в QR v2 (клиент готов пиннить) или ACME-инструкция; wss из коробки |
| 9 | Quota/rate-limit на `ai.chat` per device | телефон знакомого не должен жечь токены хоста |

## Что ядру НЕ нужно

Виджеты, темы/акценты, локализация, бэкапы, настройки уведомлений — чисто
клиентские и закрыты. STT/TTS-модели — дело плагинов хоста, ядру нужны только
контракты из п.3–4.

## Рекомендуемый порядок

```
1. Pairing ticket      (P0, малый, развязывает руки демо)     → vynkor + wire
2. Chat streaming      (P0, самый заметный UX-эффект)          → wire + vynkor
3. E-01 per-device keys (P0*, XL, можно параллельно с 2)       → все репо
4. Capability audit    (P1, дёшево, сильно повышает доверие)   → vynkor
5. Assistant session   (P1, перед wake-word волной клиента)    → vynkor + плагины
6..9                   (P2, по мере контакта с пользователями)
```

\* E-01 можно начинать после обсуждения RFC; п.1 его не блокирует, но ticket-механизм
стоит проектировать сразу с учётом передачи публичного ключа.

## Открытые вопросы

2. Формат стриминга: новые фреймы `CHAT_DELTA` vs переиспользование event-шины?
3. Кто владелец assistant-пайплайна — ядро или отдельный плагин-assistant?
